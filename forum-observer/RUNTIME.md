# 论坛采集运行核验（2026-10-17）

本页描述当前运行机制，旧 README 中历史时间表不代表当前配置。

- 主入口仍为 GPT 19:40 触发和既有 daily cycle。19:40/45/50、20:00 GitHub cron 保留，cron 可能延迟，不能把配置存在当作已启动。
- 修改采集代码/测试/工作流后立即运行离线测试；18:50 增加提前测试。正式采集前继续保留全部测试，不允许绕过。
- 实际采集开始时重新计算时间预算：单次不超过30分钟，北京时间21:00硬截止。预留90秒及进程收尾时间，临近截止可少于30分钟，窗口关闭不能再启动采集。
- 20:30只检查进度；未结束不标为完成。最终报告由原采集/归档流程生成。既有冻结存在时不重复采集。
- `status/latest.json` 和 `status/runs/<run>-<attempt>.json` 分别记录最近状态及各次运行。采集中约每60秒上传一次；若上传失败，必须以实际 Actions 步骤/产物核查，不能猜测。
- 有效进行的证据：当前期号、正文尝试/成功打开/提取/完成数、最近验证正文的作者和URL、提取时间、长度和SHA256。加精与普通正文分别统计，不使用评论指标。
- 仅在最近120秒确实提取了经过详情校验的非空正文时，状态可为 `collecting_effectively`；只有任务运行或时间戳跳动为 `collecting_unverified`。正文有效不等于推荐玩法有效，计分仍通过原规则校验。
- 独立 watchdog 在采集工作流结束后以及19:47/57、20:07/17/37核验真实步骤。5分钟无进度或无最近验证正文时告警，不自行覆盖冻结或杀掉其他任务。
- 无启动、明确基础设施/网络失败才允许补救，最多3次/北京时间日期。派发请求接受不等于采集成功；后续通过实际步骤和正文证据确认。
- 测试/校验失败、未知错误不盲目重试：记录具体失败步骤，产生失败的 watchdog 运行和 Actions 错误标记。GitHub站外推送是否送达由用户通知设置决定，本改动不声称已配置手机通知。
- `status/recovery/YYYY-MM-DD.json` 保存检查时间、真实运行链接、状态、失败步骤及补救次数。已冻结、已有运行、窗口关闭时不额外启动。
- watchdog本身也依赖GitHub事件投递，不保证cron准点；GPT是另一个核验入口，两端均不可达时不能声称运行正常。
